# peblish

peblish is an open-source, ActivityPub-federated, Reddit-style community platform written in TypeScript (TanStack Start, Mux UI, an ActivityPub implementation of its own tested against Fedify). Its flagship instance is [feddit.com](https://feddit.com). Phase 1 (the feddit.com cutover MVP) is under way; the plans live in `/Users/admin/.agents/plans/feddit/` on the maintainer's machine (to be published with the first product milestone).

Packages export source through subpath wildcards (`@peblish/core/tx/tx`), with no barrel files. In `@peblish/ui`, `.tsx` modules are imported without an extension (`@peblish/ui/components/button`) and `.ts` modules with it (`@peblish/ui/tokens/spacing.ts`). `pnpm lint` enforces the package boundaries (`.dependency-cruiser.cjs`, with a failing fixture per rule in `tests/boundaries.test.ts`). `tests/source-guards.ts` covers what that lint cannot see. Product code has no computed `import()`, `require`, `createRequire`, `getBuiltinModule`, `eval`, `Function` or `vm`, and no CommonJS exports. A runtime binding of the grant issuer (`authz/brand.ts`, `authz/authorize.ts`) or of the write pool (`db/write.ts`, `db/pools.ts`) may only be called, never exported, re-exported or passed on. Areas register outbox consumers, jobs, feed predicates, authz policies, inbound handlers, refusals, events and i18n catalogues by adding a file that matches a glob; `pnpm gen` writes the gitignored `*.gen.ts` registries.

The UI is built only with Mux UI, through the `@peblish/ui` facade, and `scripts/mux-guard.ts` enforces it: `pnpm lint` (and so `pnpm check`) runs it with `--enforce` and fails on any violation. It reads every script and stylesheet the build can import (`.ts`, `.tsx`, `.mts`, `.cts`, `.js`, `.jsx`, `.mjs`, `.cjs`, `.css`) in every folder of `packages/*` and `tools/*`, and skips only `node_modules`, build output (`dist`, `.output` and the like), generated `*.gen.ts` files, tests, fixtures and pure wrapper modules. The folders outside `packages` and `tools` (`e2e`, `scripts`, `tests`, `spikes`, `lab`, `vendor`) are test, build and research code the app never imports, so they are not read, and `css-import` reports a stylesheet imported from anywhere the guard does not read. It checks these rules. In markup (JSX, where a spread of an object literal counts as its props, and React's `createElement`, `jsx` and `cloneElement` however imported): `raw-element` (a raw control or structural element such as `button`, `input`, `table`, `details`, `a`, `time` or `svg` where a Mux component or a facade wrapper does the job, also through a polymorphic `as` prop or a tag held in a variable, and any `<style>` element but one whose only content is a stylesheet file imported with `?inline`), `text-element` (raw `p`, headings, `strong`, `em`, `code`, `pre`, `blockquote`, `br`: use `Text` or `Quote`), `bare-text` (words straight inside a layout element), `widget-role` and `widget-handler` (a hand-made widget: an ARIA widget role, or click and key handlers, on a plain element), `inline-style` (colours, radii, shadows or fonts in a `style` prop, or a `--muxui-*` token set there to anything but a written `var()` of a Mux token, and CSS written through the CSSOM: `cssText`, `insertRule`, `replaceSync`, `adoptedStyleSheets`, `attributeStyleMap`, `setAttribute('style')` and writes to an element's `style`), `raw-html` (`dangerouslySetInnerHTML`, `innerHTML` and the like) and `mux-import` (`@muxui/react` imported outside `packages/ui/src`). In stylesheets, where CSS escapes outside strings are decoded and vendor prefixes dropped first: `css-colour`, `css-radius`, `css-shadow`, `css-font-family`, `css-font-size`, `css-font-weight`, `css-line-height`, `css-letter-spacing` and `css-spacing` (a value that does not come from a `var(--muxui-...)` token or a `--pb-*` alias `tokens.css` defines purely from them; a `var()` fallback is checked as part of the value, and a `font` shorthand's weight and line height as those properties), `css-motion` (hand-written durations and easings), `css-infinite` (an endless animation), `css-important`, `css-blur`, `css-element-selector` (styling by tag name instead of a class, unless the element carries a `.muxui-*` class or is a descendant or child of one on every branch of the selector, `:is()`, `:where()` and a nested rule's parent selector included; a sibling of one is not inside it), `css-unknown-token` (a `--muxui-*` name Mux does not define), `css-token-value` (a Mux token or alias set to something other than tokens; an `@property` of a `--muxui-*` name is always one of these two, and any other `@property`'s `initial-value` is checked as a definition of its name), `css-import` (a stylesheet imported, by a stylesheet or a script, from outside the folders the guard reads, or a stylesheet link with a written address) and `css-mux-stylesheet` (anything but `@import` and `@layer` statements in `packages/ui/src/styles.css`, the file that imports Mux's own stylesheet). A true layout measure with no token (a width, or an offset equal to another element's size) ends its line with `/* layout */`, which waives the spacing rule for that declaration only; padding, gaps and margins a token fits never take it. An exception goes in `scripts/mux-guard.exceptions.json` as `file`, `rule`, `match` (the violation's text; for a type selector, text that every branch styling an element must contain, with `:is()`, `:where()` and nesting expanded), an optional `anchor` (the component, function or CSS rule around it), `value` (a CSS declaration's exact value), `condition` (an at-rule around it, such as a media query) and `count`, and a written `reason`; an entry that no longer matches exactly its count fails the guard, so a stale exception must be removed. Without `--enforce` the guard reports and fails only when a file has more violations than `scripts/mux-guard.baseline.json`, which is empty now that nothing is left.

Rules for writes:

- A mutation takes its target ids from `grant.subject`, never from input, and checks its invariants inside the transaction.
- A subject passed to `authorize()` is JSON-like plain data: plain objects, arrays, strings, numbers, booleans, `null`, `undefined` and bigints. `authorize()` copies and deep-freezes the subject and the principal before it awaits anything. A Date (pass an ISO string), Buffer, typed array, Map, Set, class instance, function, symbol, accessor or cycle throws `SnapshotError` (`packages/core/src/authz/frozen.ts`), because freezing cannot make those immutable.
- Set `recheck: true` on a mutation whose action a moderator, a ban or a lock can revoke: the policy then runs again inside the transaction, and a deny throws `Refused` and writes nothing. `defineMutation` enforces it for exactly `post.create`, `comment.create`, every action named `mod.*`, a person's own writes (`profile.update`, `block.add`, `block.remove`, `age.declare`, `notification.read`, `notification.read_all`, `report.create`) and report handling (`report.resolve`, `report.route`) (`requiresRecheck` in `packages/core/src/tx/mutation.ts`), in the type and with a throw at definition, so an internal mutation behind a wrapper cannot skip it; the registry test checks every exported mutation too. A mutation that must take a lock before the recheck reads its rows (`updateProfile` locks the acting actor's row; `addBlock` takes a per-blocker advisory lock) sets `recheck: 'inner'`: it takes the lock, then runs the rechecked mutation with `.within`, and throws if it did not. Other revocable actions (`vote.cast`, which a ban revokes) should set it as well; they are not enforced.
- With `lock` (set by recheck), a policy reads every row its decision rests on locked, so a revocation that updates an existing row (a soft delete, a demotion, a lock flag) cannot slip in between. Either it committed first and the recheck denies with its reason, or it waits until the write commits. Use `forShare(query, lock)` for rows no write body updates, and `forNoKeyUpdate(query, lock)` (from `packages/core/src/authz/policy.ts`) for any row a write body updates: a counter, a vote tally, the target actor row of a site ban. Reading such a row FOR SHARE and updating it later deadlocks two concurrent writers (40P01), so every policy that reads it uses `forNoKeyUpdate`; mixing the two modes on one row can still deadlock. A community ban reads its target's actor row FOR SHARE: the target's own rechecked writes hold that row FOR SHARE (the principal refresh) and then wait for the community row, so a FOR NO KEY UPDATE on it, taken after the community row, would deadlock. With `lock`, `authorize()` also re-reads the principal: the actor must exist and not be deleted, and the site role comes from `auth_user` (admin only with two-factor on). That read locks the acting actor's row FOR SHARE, so a write body must not update that row, with two exceptions: a remote community acting as itself has its row read FOR NO KEY UPDATE from the start (its row is also the community row), and self-deletion locks the owner's row FOR NO KEY UPDATE before running its rechecked inner mutation (`packages/core/src/identity/delete.ts`).
- A lock on a query that finds no row locks nothing. So a revocation recorded as an INSERT (a ban, a lock row, a removal marker) first takes FOR NO KEY UPDATE, in its own mutation, on the parent row the policies lock: the community actor row, or the target actor row for a site ban. Every policy it revokes locks that same parent row. The seed policies (`posts.ts`, `votes.ts`, `bans.ts`) follow both rules, and each lane's policy helpers do the same.
- Lock order: the acting actor's row (the principal refresh, FOR SHARE except for the two cases above), then the community's actor row, then the post, then the comment. A policy that reaches the community through a post or comment reads `posts.community_id` (and `comments.post_id`) unlocked first, locks in this order, then checks the reference again (`packages/core/src/authz/state.ts`). Counter updates keep the order too: the post, then the parent comment. A site ban locks its target actor row first, so it must not lock a community row afterwards.
- Work the instance does as itself (registration, imports, scheduled jobs) authorizes as `systemPrincipal(db, job)`, the local instance actor that migrate creates.
- No network calls inside a write transaction, and keep transactions short. Consumers read only below the oldest open write transaction on the whole Postgres cluster, so on the shared dev cluster a stuck psql transaction in one lane's database stalls every lane's consumers. The worker warns when that horizon lags more than 30 seconds.
- Every request to a host a person or a peer chose (link previews, actor and document fetches, delivery, the media proxy) goes through `safeFetch` (`packages/core/src/net/fetch.ts`; federation's seam `actors/safe-fetch.ts` re-exports it). It refuses non-public addresses with no switch; a test that needs a loopback stub uses `createSafeFetch` in a test file, and `fetch.test.ts` fails if product code imports it.

Rules for the web server:

- `packages/web/src/server.ts` is the server entry (root-owned). It sends federation requests to `@peblish/federation/http` before any UI route matches, then adds the security baseline from `packages/web/src/server/headers.ts` to every HTML response. Lanes extend that baseline there, not per route.
- Federation answers the ActivityPub endpoints (`/ap/*`, WebFinger, NodeInfo, the inboxes and outboxes) always. It answers `/`, `/u/<name>` and `/c/<name>` only when Accept asks for ActivityPub JSON; otherwise, or when federation declines (`null`), those paths render the UI page. Every response on them, from either side, carries `Vary: Accept`. Imported feddit.com actors keep their ap_ids (contract 6), so `https://feddit.com/u/<name>` and `/c/<name>` are both the ActivityPub id and the human page.
- Lane FED-A owns `packages/federation/src/http.ts`, `federation.ts` (the software identity, `localOrigin()` and `userAgent()`), federation's consumers (`packages/federation/src/<area>/consumer.ts`, run by the worker beside core's) and jobs, the area directories `actors/`, `webfinger/`, `nodeinfo/`, `signing/` and `delivery/` under `packages/federation/src/`, and the bridge `packages/web/src/server/federation.ts`. Serving (actors, collections, WebFinger, NodeInfo), delivery, signing and signature verification are peblish's own code, and Fedify is a test-only dependency (an independent implementation the signing tests check against); `packages/federation/README.md` describes them. Web imports nothing else from federation but the job registry the worker also runs and lane DISC's resolver entry `resolve/web.ts` (lint rule `web-federation-entry-points`).
- The root route loads `{ locale, prefs, session, shell }` once (`shell/root-data.ts`, `staleTime: Infinity`): a feature that changes the session or the sidebar's lists calls `router.invalidate()`. A server function called from inside another one is missing from the production build's function table, so a loader calls the plain functions (`pageSession()`, `loadShellData()`), not server functions.

## Outbox and migrations

- `processBatch(consumer, limit = 100): Promise<number>` (`packages/core/src/outbox/worker.ts`) runs one batch for one consumer in one transaction. It scans up to `limit` outbox rows after the consumer's cursor in `(tx_id, id)` order, below the oldest running transaction. It hands the consumer the rows of its event types and moves the cursor past every scanned row. The result is the number of rows the cursor moved past, matching or not, not the number of events handled. It returns 0 when the consumer is caught up, backing off after a failure, or locked by another worker. The worker loop runs again at once while that number is above 0. A handler failure (anything but `Refused`) is counted against its event on the cursor row; once the same event has failed 10 times over at least 30 minutes, the next batch skips it, logs it, writes it to `outbox_skipped` (`packages/core/src/outbox/tables.ts`) and counts it in `outbox_cursors.refused`. Counting is a write, so a database outage never reaches the threshold.
- `runMigrations(url, { folder?, after? }): Promise<void>` (`packages/core/src/db/migrate.ts`) applies pending migrations from `folder` (default: core's `drizzle/`, or `PEBLISH_MIGRATIONS_DIR`) on a dedicated connection. That connection holds `pg_advisory_lock(hashtext('peblish.migrate'))` through the migrations and through `after` (the instance bootstrap in the `migrate` process), and releases it in `finally`. Concurrent migrate runs take turns, and the later ones find nothing pending.

## Ownership

Root owns the lockfile, the drizzle journal and migrations, the root configuration, CI, the `Dockerfile`, `vendor/`, `packages/core/src/{db,tx,outbox}/**`, `packages/core/src/authz/brand.ts` and the shared schema files (`views.ts`, `entities.ts`, `ids.ts`, `registry.ts`, `site-settings.ts` in `packages/schema/src/`). Report a needed change there instead of making it.

A lane edits the schema files its write set names: `authz.ts` and `modlog.ts` for AZ; `identity.ts`, `session.ts` and `invite.ts` for A; and each area's `refusals/<area>.ts` and `events/<area>.ts`. A lane may add dependencies to its own package's `package.json` with exact versions, listing each in `LANE-NOTES.md`. Root regenerates the lockfile and the migrations at integration.

Every file G0 created has one owner. In wave 3 (rows COMM to LAB) the action slots `-ui/actions/{report,moderate,block}.tsx` on the post page, the comment row, the profile and the community page belong to REP, MODF and E1 by file name, whichever tree they sit in, and each lane appends its own entries to `e2e/payload/routes.ts`. A test file belongs to the owner of the file it tests, and a generated `*.gen.ts` to nobody (`pnpm gen` writes it). A lane changes another owner's file only through a request to that owner (root for root's).

## Development

Node 24 (`.nvmrc`), pnpm 10 (`packageManager`), Docker for the local services.

```sh
pnpm install
docker compose up -d --wait        # Postgres 17 on 18432, MinIO on 18490/18491, Mailpit on 18425/18426
lane_env=$(sh scripts/lane.sh g0) && eval "$lane_env"   # this lane's database, port, test database, S3; stops on failure
pnpm check                         # build, typecheck, lint (boundaries, oxlint, prettier), tests
pnpm e2e                           # Playwright against the build, on $PORT; BASE_URL=<url> pnpm e2e targets a running server instead (no DATABASE_URL needed)
                                   # *.serial.spec.ts (specs that save a shared site setting) run one at a time in a second run after the rest, whether or not it failed (e2e/run.ts); pnpm e2e --project serial runs them alone
                                   # E2E_SHARD=1/2 pnpm e2e runs one of CI's two runners' parts (the serial specs run on the last); scripts/e2e-shards.ts checks the parts add up
pnpm dev                           # pnpm gen, then the dev server on $PORT
```
