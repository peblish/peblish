# Remote fetch, backfill and dormant instances (lane REM)

What we remember about peers beyond the document they sent, and how we get the rest.

## Cache figures

`ttl.ts` is the one table (`remoteTtls`). A stored remote actor is fetched again on use after a day (`resolveRemoteActor`), a key that stops verifying makes one refetch of its actor, at most one a minute, a peer's NodeInfo is read again after a day, mirrored moderators expire after twelve hours. The first five are imported from the code that applies them, so the table cannot drift. `ttl.test.ts` checks them on a fake clock.

## Fetching on purpose

- `object.ts`: `fetchRemoteObject(apId, { vouch })` reads a post or comment from its own origin and stores it through the mutations the inbound handlers use (`storeRemotePost`, `storeRemoteComment`), authorized as its author. A `Vouch` names the remote community that stands behind the object: it served the object in its own collection, or announced an activity about it. An object nothing vouches for is not stored. A comment's missing ancestors are fetched first (`maxParentDepth`). A 410 or a `Tombstone` is a deletion (`deleteRemoteObject`, one ledger row). `readObject` is the one place a peer's object is read, and it holds what it reads to the URL asked for: the document's id (fragment stripped) must be that URL, or the one it was served from, on the server that served it (`object.id_mismatch`), so a listing of `evil.test/x` cannot store `good.test/post` as someone else; an id on this server's own origin is refused without a request (`object.local`). `storeObject` takes a `confine` for bulk readers: posts only, or comments on one given post (parents are then never fetched).
- `actor.ts`: `refreshRemoteActor(apId)` fetches now. 410 or a Tombstone deletes the actor (`deleteRemoteActor`); a valid document for an actor we hold as deleted because of a 410 or a Tombstone undeletes it and stores the document. An actor that sent its own signed Delete (ledger cause `Delete`) stays deleted whatever is served; only its Undo(Delete) restores it (`undeleteRemoteActor` checks the ledger under the actor's row lock, so a Delete that lands during a refresh wins).
- `missing.ts` and `job.ts` (`federation.missing_objects`, every minute): the inbound pipeline skips activities about an object we never saw as `target.missing <ap_id>`. This finds those targets among the skipped rows (one row for each object and announcing remote community, newest first, a page at a time, so a crowd of objects it will not ask for does not hide an older one that it can), fetches each from its own origin under the vouching of the community whose Announce carried the activity, and stores it. Storing puts the waiting rows back to pending (`requeueSkippedFor`); an object that is held already but whose rows still wait (a store cut off before its requeue) puts them back before it settles. What a process remembers is keyed by community and object, capped and expiring: an object that is gone or refused is not asked for again by this process for a day; one whose server is down is asked for again after growing waits.
- `recheck.ts` and `recheck/job.ts` (`federation.recheck_objects`, every ten minutes): a held remote post or comment is asked after at its own server once a day, 100 a run, oldest first (`core/src/remote/rechecks.ts` picks and marks them in one statement, table `object_rechecks`), so a 410 or a Tombstone for it is found even though the peer never sent a Delete. Our copy is soft-deleted and the ledger gets its row.
- `polite.ts`: one request at a time to a host, with a gap after each. The backfill and the missing-object job use it.

## Backfill

`../backfill/`: the consumer `federation.backfill` queues a community (`backfills` row) when our follow of it is accepted (`follow.accepted`, local follower, remote Group). The job `federation.backfill_run` (every 30 seconds) claims one under a lease and runs it: refresh the community, then read its `featured` and `outbox` collections, store each post, and for a post that offers a `context` or `replies` collection (FEP-7888) its comments. An embedded object is trusted only when its id is on the community's own origin (and is the id the listing names); any other is read from where it lives. Only posts come from the community's collections. A post's `context` or `replies` collection is its author's, so it is read only from the post's or the community's server, only after the community itself listed the post, and it yields comments on that post alone: a comment is stored once what it replies to is the post or a comment already stored from that collection, whatever order they are listed in, and a Page or a reply elsewhere is refused. Caps are data in `core/src/remote/backfill.ts` (50 posts, 100 comments a post, 250 requests). A run holds a claim (its attempt number and its lease) that `settleBackfill` must match, so a worker whose lease ran out cannot settle what another took over, and a run makes no request in the last minute of its lease. What Lemmy 0.19.21 and PieFed 1.8.11 serve: a community's `outbox` (Lemmy: Create activities of its last posts) and `featured` (pinned Pages), advertised on the Group document; their Pages and Notes carry no `context` or `replies`, so comments are not backfilled from them, only fetched when something names one.

## Dormant instances

`core/src/remote/dormant.ts`: an instance whose deliveries have been failing for seven days (counted from the first failure the health job saw, `instance_health.failing_since`, not from the age of the queued rows) and that sent nothing in that time is dormant; `isDormant(instanceId)` (called by the delivery worker for each row) says yes, except once a day, when it lets one delivery through as a probe. A delivered probe or any activity from the instance revives it; a probe that shows no sign of having been tried an hour after it was claimed (the worker died first) is given back. The job `remote.instance_health` (every ten minutes) derives all of it from `deliveries` and `inbox_raw`; the figures are `dormancy` in that file.

## Retention

`core/src/remote/prune.ts`: settled inbox rows go after 14 days, settled deliveries after 30, `inbox_dedupe` markers after 90, ended `throttles` windows after one (job `remote.prune`, hourly). Candidates are claimed with `FOR UPDATE SKIP LOCKED` and the DELETE repeats the state and cutoff conditions, so a skipped row the inbox job puts back to pending is never deleted.

## Remote deletion

`core/src/remote/actors.ts`, `ledger.ts`, `objects.ts`. `deleteRemoteActor(grant, { removeContent, cause })` is not one transaction: the actor is tombstoned in its own (`tombstoneRemoteActor`: profile scrubbed, ledger row for a request that adds to what is recorded), then its posts and comments go one post at a time (`removeActorContentUnderPost`), each in a transaction that locks the community, then the post, then the actor's comments under it in path order, as every comment writer does; the actor's row is not held while those locks are waited for. Call it outside an open transaction (the inbound handler does so in `prepare`). It returns `{ actorChanged, contentRemoved }`, independent of each other: content removal runs for every request that asks for it, whatever the actor's earlier state. `recordDeletion(t, { kind, id, cause, actorId, removeContent? })` writes one ledger row in the caller's transaction (reasons `remote.actor_deleted`, `remote.author_deleted` for an author's own Delete, `remote.object_gone` for a 410 or Tombstone, and `remote.actor_undeleted`). `storeRemoteActor` lets a Person become a Service and back, and throws `RemoteActorKindError` for any other change of kind.
