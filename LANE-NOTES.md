## 4. Decisions and deviations

1. Added one action, `media.scan_claim` (system `scheduled`, subject `{ mediaId: Uuid | null }`; `claimScan`), because leasing rows is a write and every write is a mutation. `null` takes the next due batch, an id takes that one row (the inline scan). Added one refusal, `media.hold_invalid` (a hold needs a reference up to 200 characters and a future date). Deviation from the contract's lists, additive.
2. `media.scanned` is `{ mediaId, from, to }`: clean and failed scans, and the undecided expiry (`quarantined` to `blocked`). `media.quarantined` carries evidence id, source, classification and `from` (`pending` or `clean`). `media.purged` is `{ mediaId, cause: 'blocked' | 'failed' }`, emitted when the key is cleared. `media.reviewed` has no post count: posts are removed after the confirm transaction, one `mod.remove` each.
3. The expiry (`expireUndecided`) blocks the image but does not remove posts: `mod.remove` needs a moderator or admin, and the system principal has no such authority. Posts that show a blocked image get a 404 image until an admin removes them. Only a quarantine caught by a late list entry can have live posts (an upload is never posted before it is clean).
4. Admin writes (`confirmMatch`, `releaseMatch`, `recordHold`, `addBlockedHash`, `removeBlockedHash`) also write a **private** modlog row (`public: false`, no target, no reason) named by the action (`media.review`, `media.blocklist`), per the rule that an admin write leaves a modlog row. The evidence log carries the detail. MODF: these rows have no community and a non-`mod.` action; they never reach the public read model.
5. The undecided window runs from the quarantine (the evidence row's creation), `MEDIASCAN_UNDECIDED_PURGE_DAYS` (default 7), and a hold in force stops it. A confirm also tries to delete the bytes at once (best effort); the 60 s job is the backstop.
6. A hold is accepted on an undecided image, or a confirmed one whose bytes are still stored. It sets `hold_until`; `retain_until` becomes the later of decision plus 24 months and the hold date. A released image, or bytes already purged, is `media.already_decided`.
7. One evidence row per image (`media_id` unique): a released image caught later by a new list entry reopens the same row (`requarantined` in its log).
8. `MEDIASCAN_LOCAL_ONLY=1` means list only: configured providers are not called. With it unset and no provider the scan is `failed` at once (not retried); provider errors and timeouts retry up to 5 attempts on the job and are final on the inline path.
9. The Arachnid adapter reads `classification` (required) and `match_type` (`exact` or `near`), else a non-empty `near_match_details` means `near`, else `null`. Both the Basic scheme and the `match_type` field name are assumptions to confirm on the account's API page (decisions.md). The raw answer kept in a manifest is the response body, capped at 16 KiB (a larger one keeps its classification and `truncated: true`); an answer over 64 KiB is refused. Redirects are never followed. `version()` returns the response as JSON text capped at 200 characters; the tab does not call it (no network call on a page load).
10. A confirmed `test` classification lists its hash as `other`; `csam` as `csam`; `harmful-abusive-material` as `other`; a list-sourced case keeps its category.
11. The tab follows the mock's sub-sections as plain links (`?section=review|failed|hashes|evidence|status`, `?item=<media id>`), the decision control as three exclusive `<details name="decision">` panels with plain POST forms, so it works without JavaScript. Not built: "End hold and purge" on an evidence row (no core action; the hold ends with its date), and a "version check ok" line in the status strip. The status line shows `uploads.enabled` and `remote_media.enabled` read-only with a Settings link, as the brief says.
12. `error.media.rejected` and `error.media.scan_unavailable` already exist in `w/i18n/media.json` (GW3's composer codes), so `mediascan.json` holds only the admin page's keys (`media.*`, and `error.media.*` for the five refusals the page can show, plus `auth.*`, `target.not_found`, `form.invalid`, `generic`). German copy is mine and unreviewed.
13. The e2e pause-switch case (`remote_media.enabled` off: proxy 404, clean `/media/<id>` 200) is opt-in, see request 3; the identical-404 check over every non-clean state and the clean upload's exact headers run by default. `e2e/composer/uploads.spec.ts` needed no edit: with `MEDIASCAN_LOCAL_ONLY=1` the server scans against the list only and the upload completes. Without it that spec's last case fails with `media.scan_unavailable`, which is the intended fail-closed behaviour (request 3).
